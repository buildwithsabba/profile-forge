# The prompt

Copy everything in the block below and paste it into an agentic coding tool
(Claude Code, Cursor, Codex, Copilot Agent) inside an empty folder.

It tells the agent what to build *and* the four things that go wrong if nobody
warns it — which is the difference between a portrait and a smudge.

---

````text
Build me an animated GitHub profile README: a terminal-style page made of three
self-contained animated SVGs, generated by Python scripts in this repo.

First, ask me for:
  1. my GitHub username
  2. the path to a photo of me (one face, looking at camera, clearly lit)
  3. the lines I want on the info card (role, what I'm building, stack, location)
Then build everything and explain each decision as you go.

## What to produce

- `ascii-portrait.svg` — my photo as monochrome ASCII art that types itself in
  row by row, then freezes. No looping.
- `info-card.svg` — a neofetch-style panel of my details, lines fading in on a
  stagger. No GitHub statistics in here; the heatmap covers those.
- `contrib-heatmap.svg` — my real 53-week contribution calendar, revealing
  diagonally, with a Less->More legend and a stats footer.
- `README.md` placing them in a centred terminal layout.
- A GitHub Action that refreshes the heatmap daily and commits it.

## Hard constraints

GitHub strips `<script>` from READMEs and sanitizes inline CSS, but it *does*
render SVGs embedded via `<img>` and plays their SMIL and CSS-keyframe
animations. So every bit of motion must live inside the SVG files. Also:

- No external stylesheets, no webfonts, no remote images — the SVGs must be
  fully self-contained. Use a monospace font *stack* of faces that ship with
  operating systems.
- No third-party stats service and no access token. Read my contributions from
  the public HTML at `https://github.com/users/<username>/contributions`.
  Day cells are `<td data-date data-level>`; the exact count lives in a
  separate `<tool-tip for="<cell id>">`, so join them by id. Levels are 0-4.
- In the README: inline `style` is stripped, so `<br>` is the only vertical
  spacing that works; `<h1>`/`<h2>` draw a full-width rule, so use `<h3>` for
  headings you don't want underlined; and a `<table>` is the only reliable way
  to put two images side by side (`valign="top"` on the cells).

## The four things that will go wrong

1. **Theme.** An SVG loaded through `<img>` cannot detect whether GitHub is in
   light or dark mode, so light-grey glyphs on a transparent background
   disappear for half of all visitors. Give every panel its own dark terminal
   background (`#0d1117`, `#21262d` border) so it renders identically in both.

2. **Polarity.** Because the panel is dark and the ink is light, the glyph ramp
   must run dark->bright: a black pixel picks the space glyph and vanishes into
   the panel, a bright pixel picks the densest glyph. This is inverted from the
   usual white-background ASCII pipeline. Use a ramp like
   `" .\`:-=+*csS#%@"` indexed by brightness. Keep it ONE colour — per-glyph
   rainbow colouring is what makes most ASCII portraits look like static.

3. **Framing.** Remove the background with `rembg`, then boost local contrast
   with OpenCV CLAHE (a flatly-lit face converts to one undifferentiated
   blob), then crush the low end with a levels curve so clothing falls to pure
   black. Crucially: measure the crop from the **alpha silhouette**, never from
   the graded image. Dark hair carries almost no brightness, so any framing
   that hunts for bright pixels crops the top of the head off. Measure head
   width as the *median* row width across the upper ~60% of the silhouette —
   the maximum catches a shoulder and leaves the face adrift in an empty panel.

4. **Whitespace.** Renderers collapse runs of spaces inside `<text>` even under
   `white-space: pre`; the surviving glyphs spread across the row and the
   portrait visibly wobbles. Emit no spaces at all: split each row into runs of
   non-space characters and place each run at its own absolute `x` with an
   explicit `textLength` and `lengthAdjust="spacingAndGlyphs"`. Alignment then
   holds in any renderer, whatever monospace face the viewer has.

## Layout

Put the heatmap full width on top, then the portrait and card side by side
below. The two panels only line up if their displayed heights match, so solve
their widths from the rendered SVG dimensions rather than hardcoding them:
with a combined width of 850, each panel's display width is
`850 * aspect / (sum of both aspects)`. Recompute this whenever the card's
row count changes.

## Structure

Put the generators in `scripts/`, sharing one module for the panel chrome and
colours. Give each generator a `STATIC=1` env var that emits a frozen frame —
previewing an animation that has already finished looks like an empty panel,
and I will waste twenty minutes on it otherwise.

The portrait and card are static art: regenerate them locally when the photo
or my details change. Only the heatmap needs the cron. So the daily workflow
should install just `requests` and `beautifulsoup4`, run the fetch and the
heatmap render, and commit with `[skip ci]` in the message so the bot's own
commit doesn't retrigger it. It needs `permissions: contents: write`.

Verify your work before telling me it's done: assert the SVGs are valid XML,
contain no `<script>` and no external references, and that no drawn element
falls outside its panel — a legend running off the right edge is the classic
failure and it is invisible unless you check the numbers.
````

---

## After it finishes

Create a repository named **exactly your GitHub username** — that is the one
GitHub renders on your profile — and push. Then open the **Actions** tab and
run the workflow once by hand to confirm it commits a fresh heatmap.

## If the portrait comes out muddy

It is nearly always the photo, not the code. Ask the agent to raise the black
point and the gamma until the ink coverage lands near 30% — it should be able
to report that number. Then try a picture with harder lighting.
